# 反馈修复与行为评测

收到失败输出或用户反馈，要求修复、优化本 Skill 时读取。先读 [主入口的修改约束](../SKILL.md) 与 [模块架构](architecture.md)，先证实问题，再改能影响实际结果的机制。

本文保存定位、修改、验证和留证的完整流程。用户反馈是排查入口，不要未经复现就认定根因；用户明确要求调整架构或维护文档时，按指定范围处理，不借此改变剪辑行为。

## 当前行为契约

- 原始口播：保留完整意思，去除有原音依据的废弃重说；语义发现与切点核验分别验证。
- 短视频：读取用户手剪参考中位数，只压缩超过目标的普通声学气口，原本更短的不补长。
- 长视频与课程：普通气口目标为 0.7 秒，较短气口不补长，保留有证据的必要操作窗口；显式模式选择优先于历史上下文。
- 手剪参考分析：只测量、对比、更新指定配置，不擅自编辑参考成片或制作最终字幕。
- 最终字幕：保持锁定时间轴，不触发粗剪。

关键失败：重复仍在却宣告全片通过、削掉低声句首、压掉必要操作、沿用错误场景参数、把合成/脚本测试当成真人主观验收。

## 本地证据

在 `evals/evals.json` 保存任务和评分要求，在 `evals/results/<candidate-id>.json` 保存结果；该目录默认排除 Git。完整媒体和转写留在临时目录，报告引用本地素材，不发布。候选标识使用文件哈希或快照，不能只叫“最新版”。

覆盖正常样本、边界样本、近邻反例、留出和旧回归。执行者若看过预期答案，该样本就不能声称是盲测留出。仅单元测试成功不能证明端到端剪辑质量。

验证等级：

1. 结构：frontmatter、引用、资源和脚本语法检查。
2. 行为冒烟：真实素材的主要任务实际执行并核对结果。
3. 留出/回归：未看预期答案的执行者在留出任务通过，旧能力无关键回归。
4. 安装交付：仅在用户要求分享后，验证 GitHub 安装和资源一致性。

如实报告最高等级和未覆盖能力。没有盲测留出支持时，新增语义规则仍属待验证增强，不宣称已经解决所有重复问题。

## 修改规则的执行细则

### 1. 先定位，再修改

先对比用户指出的位置、预期结果和实际结果；用户提供人工版本时，先做文字对比和同口径声学统计。保留当前输出与相关中间产物作为基线。沿输入到输出查找**最早出现错误的产物**，按 [模块架构](architecture.md) 定位责任模块。症状相同，不代表根因相同；未定位时可以继续读取、回放、测量，但不试探性地修改多处规则。

常见定位示例：

| 发现的问题与证据 | 应定位的模块 |
|---|---|
| 原始转写漏掉或合并真实重说，导致语义输入不完整 | M02，先处理转写证据与必要的局部复核 |
| 原稿含两遍重录，筛选稿仍错误地留了两遍，或保留了错误版本 | M02 |
| 取舍决定正确，定位出的删除边界却削掉句首或留下半句 | M04 |
| 删除区间正确，补白或气口合并后又把已删重说带回来 | M05 |
| 必要操作在保护清单中就已遗漏 | M03；若保护清单正确而后续丢失，继续查首次丢失的位置 |
| 标准正确，但实际普通气口过长或过短 | M05；若是用户要求改变标准，则为 A02 |
| 预览通过、`cutlist` 正确，实际导出却没有执行同一计划 | M07 |
| 源视频与抽轨音频从一开始就存在时间偏移 | M01；若只在导出后发生漂移，再查 M07 |
| 成片符合要求，但检测误报；或检测实现漏掉其本应检查的问题 | M06 |
| 实际视频内容正确，只是最终字幕错词、断句或时间对齐错误 | A01 |

### 2. 修改前明确范围

向用户简要说明：**定位到哪个模块、依据是什么、这次准备修改该模块的哪条规则或哪段实现。** 有足够证据且已获本次修复授权就继续执行，不把这份说明变成重复确认。

同一记录中写明允许改动的文件及章节/函数。若尚有不同根因假设，先补证据，不把猜测当成定位结论。

### 3. 一次修复只改一个责任模块

- 只修改目标模块内部的规则、实现及对应测试。模块可以跨多个文件，但修改必须服务于同一个已定位的问题。
- 不顺带优化其他模块，不因文件相邻就重构，不为局部问题更换整套工作流、转写模型或用户已确认的参数。
- 不用调整下游阈值、放宽检查或添加例外去掩盖上游错误。M06 若发现错误，应把问题退回责任模块；只有验证本身出错，才修改 M06。
- 共享的辅助函数或数据格式可能影响多个模块。优先在目标模块内局部修复并维持现有接口；不能仅因被目标模块调用，就把所有调用方都纳入改动。
- 若证据确认有多个模块分别出错，拆成多个独立修复，逐个定位、修改、验证和记录；不得把其他模块的改动混进当前修复。若无法在单模块内修复，说明具体依赖与本次尚未解决的问题；跨模块接口或架构调整不属于本次局部修复的范围，不自动执行。
- 文档与测试更新跟随目标模块：稳定的机械行为放所属脚本，数值放所属配置，语义规则放所属参考文档。主入口保留修改约束与必读路由，架构由 architecture.md 维护；不把案例不断堆入主入口。

### 4. 验证可以跨模块，修改范围仍受限

先用原案例跑真实行为验证修复，用独立样本测边界，再检查相邻模块是否仍能正常接收其输出；涉及共同基础能力时，运行相关回归。读取其他模块、运行端到端验证，不等于获准修改其他模块。

验证要检查实际结果，而不只是检查某个标记变成通过。若验证暴露新根因，返回定位步骤，建立下一项修复。修复失败时优先重算计划和短/整片音频预览；无必要时不整片重渲染，技能分析任务不需要重渲染整片视频。具体证据、评测等级和素材保存方式见本文“本地证据”。

### 5. 每次迭代留下一条可追溯记录

在本地评测结果中记录以下内容，沿用 `evals/results/<candidate-id>.json`；用户素材、原文及绝对路径不公开：

```text
问题：用户反馈位置、预期结果、实际结果
基线：修改前文件哈希或快照、原问题样本
定位：模块编号、最早出错的产物、支持该判断的证据
修改：目标文件及章节/函数、具体规则或逻辑变化
范围检查：是否触及其他模块；若有，拆分处理说明
验证：原问题结果、相关回归、已验证与未验证范围
结论：本次是否解决、仍有何问题、回退依据
```

结束时向用户说明“本次改了哪个模块、为什么、怎样验证”。不以通过某个局部测试代替整片质量结论，也不把不同轮次的改动混为一次成功。

如果文字对比不能确认用户最初怀疑的重复漏删，就明确收窄结论；不要发明一次漏剪来证明修改必要。
